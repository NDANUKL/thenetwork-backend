# Submission recovery and duplicate location metadata

On 26 October 2026, the customer intake returned HTTP 409 DuplicateEntryError for a DD Request Site primary key. Read-only live metadata inspection confirmed two Field Request DocField definitions named project_locations, both Table fields pointing to DD Request Site. Frappe traverses both table definitions when inserting children, so the same child row is inserted twice and the transaction rolls back. Similar job descriptions, changed suppliers and changed contact details do not define a duplicate request.

The native Field Request JSON now contains one project_locations field. Normal model sync preserves the DD Request Site table and existing records. The post-model-sync deduplicate_project_locations patch force-reloads the corrected native metadata and verifies that one table definition remains. It does not delete location records, reset request numbering, alter uniqueness constraints, or touch retired scripts.

Validation: run python -m unittest discover -s tests -p test_doctype_schema_integrity.py offline. On a backed-up staging site deploy this revision, run normal bench migrate and the Field Request model tests, including test_location_children_are_inserted_once_and_keep_source_identity. Check that metadata contains one project_locations table, submitting contact-based and pinned locations succeeds, repeat saves keep one child per destination, and source_site_id still links distinct source and operational location records. Deploy the same native revision through the normal release process and clear site caches. Do not rerun completed handover patches. Local source checks do not establish that this repair has been deployed.

The companion website change uses a 60-second recoverable lease, checks the database before another creation attempt, binds an assessment submission ID to its normalized snapshot, and charges creation limits once per verified ID. Changed details on an already started submission require resolving the original or preparing a new assessment. Definite backend rejections release their lease; ambiguous timeouts retain it briefly and retry with the same ID. The database submission_id uniqueness constraint remains the final duplicate guard.
